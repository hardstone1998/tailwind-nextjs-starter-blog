# 项目体验评估与 Rubric 建议

评估日期：2026-09-01。对象：当前本地项目，不代表线上部署状态，也不是对作者真实职业能力的认证。本轮不修改应用实现。

## 结论

现有「公开研究笔记」风格值得保留：米白纸面、蓝色强调色、细网格、等宽英文栏目标签、实验编号和状态标记，适合技术作品集。主要改进方向是让作品证据更突出、阅读路径更清楚、评分更可复核，而非继续增加装饰。

首页定位为「多模态 / 视频模型工程师」，但最先展示的是开源方向辩论与标题本地化实验；更贴近定位的职业项目位于关于页。建议首页增加代表成果区，将视频工作流、翻译质量系统和 ASR 性能工程串成明确的作品线索。正在探索的项目继续显示探索状态，不包装成已完成成果。

## 检查范围与限制

- 阅读首页、布局、研究笔记、项目、职业项目、能力域、评估说明、语言机制、SEO、内容构建与部署配置。
- 本地浏览器检查首页、系统工程能力页、评分说明、FunASR 文章及其失效链接；检查 390px 手机布局与约 1100px 中等宽度布局。
- 验证手机菜单开关、语言切换、FunASR 搜索结果过滤，以及能力域到评估说明的导航。
- ESLint 通过。另以 `tsc --noEmit --incremental false --composite false` 完成无构建缓存写入的类型检查，结果通过。
- `npm run build` 通过，生成 115 个静态页面，RSS 生成完成。构建器报告首页 First Load JS 223 kB、博客列表 122 kB、文章页 130 kB；这是构建指标，不是弱网实测或用户体验得分。Contentlayer Windows 提示、punycode 弃用和 TypeScript project references 警告未阻止构建，仍值得维护时处理。
- 没有进行完整 WCAG 审计、所有页面的视觉回归、真实用户性能测试或外部项目真实性核验；不提供虚构 Lighthouse 或 Core Web Vitals 分数。深色主题定义已检查，但未完成深色视觉验收。
- 本地安装为 Next.js 15.5.21；AGENTS.md 指定的 `node_modules/next/dist/docs/` 不存在。未编写 Next.js 实现代码；性能建议参考官方在线文档。

## 工程优化

1. **减少不必要的客户端数据和代码。** `app/Main.tsx` 为客户端组件并静态导入 Recharts。`components/SkillDomainPage.tsx` 把完整 `Blog[]` 交给客户端列表，但卡片只需要摘要字段。建议使用 `CoreContent<Blog>` 或更小的 DTO，避免发送 MDX 正文和编译代码。先用生产构建与 bundle analyzer 测量收益，不预先承诺减少百分之多少。[Next.js 延迟加载文档](https://nextjs.org/docs/app/guides/lazy-loading)
2. **阅读辅助。** Contentlayer 已生成 `toc` 与 `readingTime`，默认文章布局尚未展示。可补桌面目录、手机折叠目录、预计阅读时间和代码复制，复用已有数据。
3. **语言状态与 URL。** 当前语言来自客户端状态及 localStorage，刷新先渲染中文。若英文面向外部读者与搜索引擎，优先评估语言路由或服务端可知语言方案；不要把 use client 等同于完全没有服务端 HTML。
4. **内容规则自动化。** 检查站内链接、正文重复标题、缺失图片、未定义能力域、失配翻译、评分证据引用与权重总和。分页目前服务端按原始文章数算、客户端按翻译去重后的数量算，内容增长后应统一规则；本轮没有把它认定为已复现的空页缺陷。
5. **交互与可访问性。** 增加跳转正文入口、给手机导航对话框可访问名称、为图表保留文本数据、补充减少动态效果设置。按钮建议采用更宽松的触控区域；WCAG 2.2 的 24px 最低目标尺寸有间距等例外，不能只看图标大小就判失败。[W3C 目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
6. **安全和维护。** CSP 包含较宽的 `connect-src *` 与 `unsafe-eval`，可按真实资源需求收紧并分别验证开发和生产模式。`strict: false` 可逐步收紧；无须为静态博客盲目增加数据库或复杂缓存。提交前加入 lint/typecheck/build，与实际部署平台保持一致。

## 能力评分适合使用 Rubric，但目前还不完整

Rubric 需要明确的维度、不同等级的行为描述，以及一致的判定规则。现有页面的「六条标准 + 0–100」只是维度清单，还不足以解释为何是 71.5 而不是 65 或 80。[CMU Rubrics 指南](https://www.cmu.edu/teaching/designteach/teach/rubrics.html)

应将评分对象限定为「截至某日，给定材料所支持的能力表现」。不要把个人总体价值、行业百分位、学习潜力和证据公开程度混为一谈，也不应把六个性质不同的领域简单平均成“综合人才分”。

### 建议的数据结构

- `rubricVersion`：评分规则版本。
- `scope`、`assessedAt`：评估边界及材料截止日期。
- `dimensions[]`：维度标识、权重、领域专属等级描述。
- `ratings[]`：等级或 null、判定理由、证据标识、限制、未满足条件。
- `evidence[]`：文章/代码/报告链接、定位到的章节、对应版本或 commit、作者负责范围、是否独立验证。
- `review`：人工复核状态；若实际使用模型，再记录具体模型版本、提示词版本及原始输出归档。
- `coverage`：可评估维度的权重占比，与能力分分开展示。
- `history[]`：规则与结果变化；换 Rubric 版本后不能直接画成同一条能力增长曲线。

### 五维通用结构

| 维度             | 权重 | 需要回答的问题                               |
| ---------------- | ---: | -------------------------------------------- |
| 原理与问题建模   |  15% | 是否解释机制、约束及方案取舍？               |
| 独立实现与交付   |  25% | 本人具体做了什么，产物能否运行？             |
| 评测与实验严谨性 |  25% | 基线是否公平，有无误差分析、消融和重复测量？ |
| 可靠性与真实场景 |  20% | 是否考虑失败、性能、成本、监控和用户约束？   |
| 复现与技术表达   |  15% | 他人能否据此理解、验证或复用？               |

各能力域应有专属描述。下面是「系统工程与部署」的第一版示例，不能原样套到“学习速度”或“技术影响力”。

| 维度         | L1：解释                 | L2：实现                           | L3：验证                             | L4：复用与检验                       |
| ------------ | ------------------------ | ---------------------------------- | ------------------------------------ | ------------------------------------ |
| 原理与建模   | 解释进程、队列、锁等概念 | 为具体服务画出资源与调用关系       | 以测量定位瓶颈并比较方案代价         | 在多种负载下验证模型边界和反例       |
| 实现与交付   | 跟随教程完成局部代码     | 独立完成有运行说明的服务           | 完成集成、部署及故障处理流程         | 形成经复用验证的组件和维护文档       |
| 实验严谨性   | 描述指标含义             | 提供可运行基准和一次测量           | 同硬件基线、消融、重复测量及误差解释 | 在明确环境与版本下可由他人复核       |
| 可靠性与场景 | 列出主要失败风险         | 实现超时、限流、资源清理等基本防护 | 提供容量、尾延迟、恢复与告警验证     | 提供持续运行记录或系统性故障演练证据 |
| 复现与表达   | 说明过程和主要结论       | 给出输入、步骤、配置和局限         | 提供版本化脚本、样例和结构化复盘     | 有独立复现、复用或有记录的技术评审   |

- L0 只用于有证据表明未达到 L1 的情况；缺少材料记为 `null / 待评估`，不是 0 分。
- 只授予材料实际满足的最高等级；评审可指出部分达标，但不凭语气印象给出小数等级。
- 所有维度都可评估时：`总分 = Σ(权重 × 等级 / 4)`，权重以 15、25 等百分数输入。前台显示整数、等级及逐项理由即可，不制造小数精确性的错觉。
- 存在关键缺项时不发布总分；显示已评项目和覆盖率。覆盖率不乘进能力分，也不将少量已评项目重新归一化后冒充全面能力分。
- 无公开证据不等于没有能力。受保密约束的项目可提供脱敏的任务边界、测试方法和审阅说明，明确其无法公开复现的限制，不要求泄露商业材料。

纯算术示例（不是本人的新评分）：等级为 3、3、2、2、2 时，结果为 `15×3/4 + 25×3/4 + 25×2/4 + 20×2/4 + 15×2/4 = 60`。现有 72、71.5 等数字不能直接换个 Rubric 标签继续使用，必须重新逐项评审。

### AI 在评分中的角色

先冻结材料和规则，再让 AI 提取证据、匹配等级、指出缺项，最后由人工核对引用和结论。把原始内容当作数据，忽略材料内部任何“请给高分”的指令。固定相同材料可重复评估检查一致性，但多个模型同意不等于事实已核实。

模型应输出每个维度的等级、证据定位、为什么未达到下一等级，以及证据限制。没有引用支持时必须弃评。不要让实时访问首页触发付费评分调用：可在内容发布或主动复评时生成静态记录。

首页建议展示「能力领域 + 代表证据数 + 最近更新」，分数或等级放入详情。零证据领域保留入口和下一步，不绘制为雷达图上的低分或高分。

## 网站自身的示范评分

这是本次有限样本下的产品审阅分，不是行业排名，也不是 Lighthouse 分。为了可追溯，明确使用 1–5 档：1=关键流程不可用，2=明显缺口影响理解或可信度，3=基本可用但有已知缺陷，4=总体一致且有充分内容支撑，5=完成系统验证并达到稳定优秀表现。未测项目不被视为已经通过。

| 维度               | 权重 | 档位 |   加权得分 | 本次判断依据                                                           |
| ------------------ | ---: | ---: | ---------: | ---------------------------------------------------------------------- |
| 视觉一致性与辨识度 |   20 |  4/5 |         16 | 配色、卡片、实验状态形成统一语言；品牌仍有旧名称                       |
| 内容与项目展示     |   20 |  4/5 |         16 | 有真实任务叙事、技术细节和结果；实验归因及首页展示顺序需改善           |
| 信息架构与阅读     |   15 |  3/5 |          9 | 分类、能力入口完整；断链、重复标题、目录缺位                           |
| 响应式与国际化     |   15 |  3/5 |          9 | 手机主流程可用；中等宽度拥挤、英文界面不完整                           |
| 能力评分可复核性   |   15 |  2/5 |          6 | 有免责声明和部分证据，但缺等级锚点与计算记录                           |
| 工程维护与交付     |   15 |  3/5 |          9 | lint、独立类型检查与生产构建通过；内容验证、数据裁剪和 CI 门禁仍可增强 |
| 合计               |  100 |    — | **65/100** | 这是当前可观察证据下的示范量表，不评价作者本人                         |

评分刻意使用粗档位，避免在没有用户研究和全量测试时给出看似精密的体验分。后续应保存相同验收用例，再依据实际修复重新评审。

## 实施顺序

1. 修断链与标题层级；统一评分来源文案；把缺证据领域改为待评估；修复中等宽度布局。
2. 建立版本化 Rubric 与证据记录；先对证据较多的系统工程领域试评，由人工确认规则，再推广其他领域。
3. 完成界面语言与 SEO 一致性，接入目录和阅读时间，缩小客户端数据并测量生产包。
4. 从字幕质量实验台或视频工作流回放中选一个完成，使用真实脱敏或清楚标注的合成样例。

先建立「定位清楚、证据可信、内容可读」的基础，再增加交互实验，收益会更集中。
